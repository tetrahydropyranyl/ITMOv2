Tree of Thoughts: улучшение артефакта unit‑проверок

Цель

- Проанализировать артефакт practices/practice_01/tests_unit.md на предмет слабых мест и подготовить исправленную версию того же формата.
- Сохранить результат в practices/practice_02/tree_of_thoughts/tests_unit_v2.md.
- Обновить practices/practice_02/tree_of_thoughts/experiment.md: заполнить все оставшиеся разделы по шаблону Tree of Thoughts, присутствующие в файле (только «Внешне описанные альтернативы», «Выбор», «Что изменили в исходном артефакте»). Не добавлять новых разделов или таблиц. Раздел «Запрос» не менять.

Разрешённые входы

- practices/practice_01/tests_unit.md — целевой артефакт для анализа формата и содержания.
- practices/practice_01/TRAINING_PR.diff — факты из кода (истинный источник поведения).
- practices/practice_01/context.md — контекст: вход/выход API, ограничения, риски.
- practices/practice_01/problem.md — формулировка проблемы и метрики, обоснование негативных кейсов.

Жёсткие ограничения

- Используй только перечисленные источники. Не придумывай неподтверждённых фактов.
- Сохрани исходный формат артефакта: та же структура разделов, та же таблица с колонками:
  «Требование или правило | Что проверяем изолированно | Вход | Ожидаемый результат | Evidence».
- Язык — русский. Минимальные правки для достижения целей (не меняй названия колонок, не добавляй новые колонки/разделы).
- В Evidence давай точные ссылки на строки: файл и диапазон строк, например: app/review_service.py:19-22; app/api.py:35-37; для context.md/problem.md — номера строк.
- Не меняй иные файлы, кроме двух: tests_unit_v2.md (новый артефакт) и experiment.md (заполнение перечисленных разделов).

Критерии качества результата

1) Соответствие формату и минимальность изменений.
2) Трассируемость: все утверждения подтверждены источниками с номерами строк.
3) Полнота: учтены сильные и слабые стороны исходника; добавлены необходимые негативные и граничные кейсы.
4) Корректность: ожидания следуют из TRAINING_PR.diff и согласованы с context.md/problem.md.

Процесс Tree of Thoughts

1) READ: внимательно прочитай четыре входных файла. Составь список фактов, подтверждённых номерами строк.
2) DIAGNOSE: выпиши слабые места исходного артефакта (неполная проверка, расплывчатые Evidence, отсутствующие негативные/граничные кейсы, отсутствие проверки кратности вызовов и делегирования API и т.д.).
3) BRANCH (для каждого слабого места): сгенерируй 2–3 альтернативы исправления, которые сохраняют формат таблицы. Примеры направлений:
   - Уточнение Evidence до конкретных строк диффа.
   - Добавление строк: «ровно один вызов llm.generate», «пустой diff», «негатив: отсутствует ключ diff», «делегирование /api/reviews -> review_service.review».
   - Проверка соответствия протоколу LLM (сигнатура generate и фактический вызов).
4) SCORE: оцени альтернативы по критериям качества (выше) и присвой итоговую оценку каждой.
5) SELECT: выбери наилучшее подмножество альтернатив так, чтобы итоговая таблица была полной, без дубликатов и соответствовала формату.
6) SYNTHESIZE: собери итоговый артефакт tests_unit_v2.md того же формата, включив:
    - Заголовок «# Unit-проверки».
    - Таблицу с исходными строками, улучшенными формулировками и Evidence, а также новыми строками как минимум для: ровно один вызов llm.generate; пустой diff; негатив при отсутствии ключа diff; делегирование в review_service.review из POST /api/reviews.
    - Раздел «## Как использовали AI» в стиле исходника: кратко, без новых подразделов; при необходимости со ссылкой на prompts.md.
7) VERIFY: перепроверь каждую строку таблицы на предмет точности Evidence и соответствия источникам (номера строк обязательны).
8) WRITE:
    - Сохрани итог в practices/practice_02/tree_of_thoughts/tests_unit_v2.md.
    - Обнови practices/practice_02/tree_of_thoughts/experiment.md:
      - Заполни раздел «Внешне описанные альтернативы»: три строки A/B/C с плюсами/минусами и оценкой.
      - Заполни раздел «Выбор»: какая альтернатива выбрана, почему, как проверили.
      - Заполни раздел «Что изменили в исходном артефакте»: файл и раздел; что изменили; что отклонили.
      - Не добавляй новых разделов. Раздел «Запрос» и верхние пункты уже заполнены и трогать их не нужно.

Подсказки по содержанию таблицы (не обязательные, если источники диктуют иное)

- Формирование промпта: ожидай точную строку вида "Review this pull request and find problems:\n{diff}" (TRAINING_PR.diff: app/review_service.py:19-21).
- Схема ответа: возврат {"comment": answer} (TRAINING_PR.diff: app/review_service.py:21-22).
- Ровно один вызов llm.generate с точным промптом (TRAINING_PR.diff: app/review_service.py:19-22).
- Пустой diff: промпт всё ещё формируется и llm.generate вызывается с суффиксом перевода строки (TRAINING_PR.diff: app/review_service.py:19-21).
- Делегирование API: POST /api/reviews -> review_service.review(payload["diff"]) (TRAINING_PR.diff: app/api.py:35-37).
- Негатив: отсутствие ключа diff приводит к KeyError (TRAINING_PR.diff: app/api.py:37; context.md: 28-30, 60; problem.md: 5-9).
