# Инструкция для агента: улучшение артефакта Unit-проверки (Few Shot)

Ты — инженер по качеству. Твоя задача: проанализировать артефакт практики 1 с юнит‑проверками и подготовить улучшенную версию в том же формате с учётом контекста.

Исходные файлы:
- practices/practice_01/tests_unit.md — артефакт, который нужно критически разобрать.
- practices/practice_01/TRAINING_PR.diff — источник истины по поведению кода.
- practices/practice_01/context.md — контекст и правила.
- practices/practice_01/problem.md — формулировка проблемы и метрики.

Что сделать:
1) Проанализировать practices/practice_01/tests_unit.md на полноту, точность и проверяемость. Опираться на TRAINING_PR.diff, context.md и problem.md. Выявить слабые места: отсутствующие граничные и негативные проверки, неявные ожидания, неточность Evidence, неконсистентность терминов/формата, недостатки по покрытиям (например, отсутствие проверки числа вызовов LLM, пустых входов, кейса с отсутствующим ключом "diff" в create_review и т.д.).
2) Сформировать исправленный артефакт того же формата и структуры, поместив результат по пути practices/practice_02/few_shot/tests_unit_v2.md. Формат сохранить:
   - Заголовок: `# Unit-проверки`.
   - Таблица с колонками ровно: `Требование или правило | Что проверяем изолированно | Вход | Ожидаемый результат | Evidence`.
   - Раздел `## Как использовали AI` в конце, заполненный кратко и по делу (ссылки на prompts.md, что проверили сами). Не добавлять новых разделов.
3) Обновить practices/practice_02/few_shot/experiment.md:
   - В разделе `## Что получили` оставить Markdown‑ссылку на артефакт: `[tests_unit_v2.md](./tests_unit_v2.md)` и кратко описать результат.
   - Заполнить все остальные незаполненные разделы этого файла по существующим заголовкам.
   - Не добавлять своих новых разделов, заголовков или полей. Текст разделов `# Few-shot` и `## Примеры` уже заполнен — не изменять их.

Ограничения и стиль:
- Делаем минимальные необходимые правки, но устраняем выявленные слабости.
- Язык: русский. Код и имена — из диффа.
- Evidence указывать точно: файл и диапазоны строк из TRAINING_PR.diff там, где это уместно.
- Строго соблюдать формат таблицы и порядок колонок; не добавлять новые колонки.
- ASCII, без экзотических символов.

Ключевые моменты, которые часто упускают (проверь и при необходимости добавь в таблицу):
- Точный префикс промпта: `"Review this pull request and find problems:\n{diff}"`.
- Ровно один вызов `llm.generate` с ожидаемым промптом; отсутствие лишних вызовов.
- Возврат структуры `{"comment": <строка>}` без лишних полей; тип значения — строка.
- Пустой `diff` не ломает контракт: вызов всё равно происходит, возвращаемая структура неизменна.
- `create_review(payload: dict)` выбрасывает `KeyError` при отсутствии ключа `"diff"` — зафиксировать как негативный юнит‑кейс на уровне функции (без FastAPI‑стека), если это остаётся в текущей реализации.

Критерии приёмки результата:
1) Существует файл practices/practice_02/few_shot/tests_unit_v2.md с корректной таблицей и разделом "Как использовали AI".
2) Таблица покрывает как минимум: формирование промпта, один вызов `llm.generate`, схему ответа, кейс пустого `diff`, негатив для `create_review` при отсутствии `diff`.
3) Evidence содержит точные ссылки на строки/диапазоны TRAINING_PR.diff и/или конкретные элементы API/классов из контекста.
4) Файл practices/practice_02/few_shot/experiment.md в разделе "## Что получили" содержит ссылку `[tests_unit_v2.md](./tests_unit_v2.md)`, остальные разделы заполнены, новых разделов не добавлено.

  Требование: Формирование промпта | Проверяем: строка промпта | Ожидаем: LLM вызван | Evidence: app/review_service.py
- Стало (хорошо):
